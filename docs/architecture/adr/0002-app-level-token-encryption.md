# ADR 0002 — Application-level encryption of bank access tokens

**Status:** Accepted · 2026-08-20

## Context

Plaid access tokens are long-lived credentials that can pull a user's transaction history. They must be stored server-side to support background sync. Neon encrypts disks at rest, but disk encryption does nothing against a leaked `DATABASE_URL`, a SQL injection, a backup in the wrong bucket, a preview deployment pointed at the wrong branch, or a provider-side insider.

## Decision

Encrypt access tokens with **AES-256-GCM** before they reach the database.

- Key: `BANK_TOKEN_ENCRYPTION_KEY`, 32 random bytes (base64), generated by the self-hoster and stored only in the deployment environment.
- Per-row random 96-bit IV; **AAD = the `bank_connections.id`**, so ciphertext cannot be transplanted between rows.
- Ciphertext format `v1:<keyId>:<iv>:<tag>:<ct>`; `encryption_key_id` is also stored as a column.
- Rotation: `BANK_TOKEN_ENCRYPTION_KEY_PREVIOUS` is honoured for decryption; a `rotate-keys` script re-encrypts every row under the current key.

## Consequences

- Reading a token requires **two independent compromises**: the database and the deployment environment.
- Losing the key means re-linking banks, not losing data. This is documented prominently.
- Suspected token leak runbook: rotate the key, call Plaid `/item/access_token/invalidate` per Item, rotate `DATABASE_URL`.
- The crypto helper lives in `packages/db` (token storage is a persistence concern and `db` is already Node-only).
