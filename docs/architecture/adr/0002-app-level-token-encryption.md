# ADR 0002 — Application-level encryption of bank access tokens

**Status:** Accepted · 2026-08-20

## Context

Plaid access tokens are long-lived credentials that can pull a user's transaction history. They must be stored server-side to support background sync. Neon encrypts disks at rest, but disk encryption does nothing against a leaked `DATABASE_URL`, a SQL injection, a backup in the wrong bucket, a preview deployment pointed at the wrong branch, or a provider-side insider.

## Decision

Encrypt access tokens with **AES-256-GCM** before they reach the database.

- Key: `BANK_TOKEN_ENCRYPTION_KEY`, 32 random bytes (base64), generated by the self-hoster and stored only in the deployment environment.
- Per-row random 96-bit IV; **AAD = the `bank_connections.id`**, so ciphertext cannot be transplanted between rows.
- Ciphertext format `v1:<keyId>:<iv>:<tag>:<ct>`; `encryption_key_id` is also stored as a column.
- **`keyId` is a fingerprint of the key material** — the first 8 hex characters of `sha256(key)` — never a position in an ordering. An id derived from the key follows that key into whichever environment variable holds it, so a row records *which key wrote it*, which is the only thing a later deployment needs to know.
- Rotation: move the current key to `BANK_TOKEN_ENCRYPTION_KEY_PREVIOUS`, put the new one in `BANK_TOKEN_ENCRYPTION_KEY`, redeploy. Both are honoured for decryption, under their own fingerprints; new rows are written under the current key's. A `rotate-keys` script then re-encrypts every row, and rows it has not reached yet are recognisable by the id they carry. Remove `..._PREVIOUS` when none are left.

## Consequences

- Reading a token requires **two independent compromises**: the database and the deployment environment.
- Losing the key means re-linking banks, not losing data. This is documented prominently.
- Suspected token leak runbook: rotate the key, call Plaid `/item/access_token/invalidate` per Item, rotate `DATABASE_URL`.
- The first implementation hardcoded `keyId` as `'k2'` for the current key and `'k1'` for the previous one, which made rotation impossible rather than awkward: every row carried `k2`, so a rotation handed `k2` to the *new* key and moved the old one to an id no row had ever carried. It was invisible to the test suite because the suite built its `'k1'` ciphertext by hand — something `loadKeysFromEnv` could never do. Rotation is now tested through `loadKeysFromEnv` on both sides.
- The crypto helper lives in `packages/db` (token storage is a persistence concern and `db` is already Node-only).
- **Open (Phase 5 audit):** the `rotate-keys` script described above is not written yet. Rotation works — both keys are honoured and new rows carry the current key's fingerprint — but rows written under the old key are only re-encrypted when something rewrites them, so `..._PREVIOUS` must stay configured until a bulk re-encryption pass exists.
